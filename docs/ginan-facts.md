# Ginan 实测事实

> 这份文档记录的**全部是实测结果**，不是从文档抄来的。
>
> ⚠️ **关于网络可达性的一节尤其重要，请先读下面这段。**
>
> 网络测量是**一台机器、一个时刻**的快照。它**不能**代表所有用户。
> 这份文档里出现的"✓ 可达 / ✗ 超时"，意思是"在测量那台机器上如此"，
> **不是**"这个源不能用"。
>
> 所以工具**绝不能**把源写死成"我们测出来能用的那几个"。
> 正确做法是每个文件配**多个候选源**，运行时探测，按用户的网络挑路 ——
> 详见本文最后的「四条取数路径」。

## 二、可用的具体 URL 形态（实测通过）

### BKG —— 精密产品（免账号）

```
https://igs.bkg.bund.de/root_ftp/IGS/products/<GPS周>/
    IGS0OPSRAP_<YYYYDDD>0000_01D_15M_ORB.SP3.gz     ← 轨道，~100 KB
    IGS0OPSRAP_<YYYYDDD>0000_01D_05M_CLK.CLK.gz     ← 钟差，~1.1 MB
    IGS0OPSRAP_<YYYYDDD>0000_01D_01D_ERP.ERP.gz     ← 地球定向，~350 B
```

⚠️ 是 `RAP`（快速产品），不是 `FIN`（最终产品）。对 PPP 完全够用。

### BKG —— 天线文件（免账号）

```
https://igs.bkg.bund.de/root_ftp/IGS/station/general/igs20.atx      ← 61 MB
```

同目录还有 `igs08.atx`、`igs14.atx`、以及带版本的 `igs20_2239.atx` 等。

### BKG —— 广播星历

```
https://igs.bkg.bund.de/root_ftp/IGS/BRDC_v3/<年>/<日>/...
```

### GA —— 观测数据（免账号）

```
GET https://data.gnss.ga.gov.au/api/v1/rinexFiles
      ?stationId=ALIC
      &fileType=obs              ← 观测；用 nav 取广播星历
      &rinexVersion=3
      &filePeriod=01D
      &decompress=true           ← ⚠️ 见下
      &tenantId=default
      &startDate=2026-09-02T00:00:00Z
      &endDate=2026-09-03T00:00:00Z
```

返回 JSON 数组，每个元素有 `fileLocation`（预签名 URL，直接可下）。

**⚠️ 一个很容易踩的坑**：返回的 URL 文件名是 `ALIC00AUS_R_20262450000_01D_30S_MO.crx.gz`，
但 `decompress=true` 之后**内容是未压缩的 RINEX 明文**（实测确认：`file` 识别为 ASCII text，
gzip magic 不存在）。

> **所以：永远不要靠文件名或扩展名判断内容，要嗅探实际字节。**
> 这条规则在「文件识别」里还会再出现一次。

顺带：RINEX 文件头里有**权威的**站点标识，不用从文件名猜：

```
ALIC00AUS                                                   MARKER NAME
50137M001                                                   MARKER NUMBER
```

> 这是 GinanUI 踩过的坑 —— 它从**文件名**截前 4 个字符当站点名，
> 遇到非标准命名的文件会静默得到错误结果。

### CDDIS —— 需要账号

```
https://cddis.nasa.gov/archive/gnss/products/<GPS周>/IGS0OPSFIN_...
```

未认证时返回 **Earthdata 登录页**（HTTP 200，约 11 KB，标题 "Earthdata Login"）。

> ⚠️ **判断认证失败不要看状态码** —— 它返回 200 而不是 401/403。
> 要检查响应体里有没有 "Earthdata Login"。
> （GinanUI 的 `test_cddis_connection()` 就是这么做的，这个做法是对的。）

账号：https://urs.earthdata.nasa.gov/users/new
凭据存 `%USERPROFILE%\_netrc`（Windows，**下划线开头**）或 `~/.netrc`。

#### ⚠️ 2026-09-29 补：上面三条都**被实测修正过**

**① "未认证 → 200 + 登录页"只在**跟完跳转之后**成立。**
裸发一个请求（`requests` 或 `curl`，不带凭据）拿到的是 **302**，跳到
`urs.earthdata.nasa.gov`。200 + 登录页是**跟完跳转**的终点。
⇒ 判据仍然对（最终响应的响应体里有 "Earthdata Login"），但别拿
"状态码是 302 还是 200"去区分——那取决于你**跟不跟跳转**。

**② 认证失败**不总是** 200 + 登录页：账号密码错时是 **401**。**
实测（编造的凭据，四种情形各发一次真请求）：

| 情形 | 服务器返回 | 界面判断 |
|---|---|---|
| 完全没凭据 | 200 + 登录页 | ❌ 认证没有通过 |
| 用户名密码都编的 | **401** | ❌ 服务器返回 HTTP 401 |
| 真用户名 + 错密码 | **401** | ❌ 服务器返回 HTTP 401 |
| 真凭据 | 200 + 真数据 | ✅ 通过 |

**③ 这条链是通的**（在此之前只有推理，没有一次成功记录）：
`cddis_session()` + `cddis_get()` → `/archive/gnss/` 200；真下到
`igr21992.erp.Z`（385 B）、`IGS0OPSRAP_*.SP3.gz`（96,771 B）等，
魔数都对。而且**是自足的**：把 `trust_env` 关掉（不许 requests 读任何
.netrc）之后仍然能下 —— 也就是说它不依赖机器上的别的文件。

> 实测细节和那个把"匿名测试"变成假象的陷阱，见下面「七点二十五」。

## 三、最小文件集（M0.5 实测结论）

**用"精简 profile"跑通一次 PPP，只需要这些：**

| 文件 | 来源 | 大小 | 性质 |
|---|---|---|---|
| `igs20.atx` | BKG | 61 MB | **一次性**，缓存后复用 |
| `*_ORB.SP3` | BKG | ~100 KB | 按天 |
| `*_CLK.CLK` | BKG | ~1.1 MB | 按天 |
| `*_ERP.ERP` | BKG | ~350 B | 按天 |
| `<站号>*_MO.rnx` | GA | ~50 MB | 按天，用户数据 |

**静态文件只要一个。** 34 个 `tables/` 一个都不需要 —— 因为精简 profile 把它们对应的功能关掉了。

### 精简 profile 改了什么

从 `ppp_example.yaml` 出发，只改三处：

```yaml
# ① 关掉需要被墙文件的功能
receiver_options:
  global:
    models:
      troposphere:
        models: [standard]     # 原来 [gpt2]，要 tables/gpt_25.grd
      tides:
        enable: true           # ⚠️ 总开关，必须开 —— 见下
        solid: true            # 固体潮：**不要任何外部文件**
        otl: false             # 要 OLOAD_GO.BLQ
        atl: false             # 要 ALOAD_GO.BLQ
        spole: false           # 也不要文件，但只有毫米级，没实测就不开
        opole: false           # 要 opoleloadcoefcmcor.txt
      ionospheric_components:
        use_2nd_order: false   # 要 tables/igrf14coeffs.txt
        use_3rd_order: false

# ② 路径全写成绝对路径（见下节）

# ③ 省略 planetary_ephemeris_files（DE436，源被墙且是 GPL-3）
```

**代价**：少了海潮、大气潮、海洋极潮三项负荷改正，对流层模型更简单。
**这一点必须在界面上如实说明，不能藏。**

⚠️⚠️ **代价只有两种状态：测过的，和没测过的。**

**① 没测过就写"没测过"。**

    原来写的是"厘米级里差几毫米量级" —— **这是编的，而且是错的。**
    实测固体潮在垂直方向就有十几厘米，而它压根不该被关掉。

**代价必须如实说明，不等于必须给出一个数字。**
不知道就写不知道 —— 编一个小的，用户会拿它当依据做判断。

**② 现在这几项测过了（2026-09-20），所以要照实写。**

    某测站 2026-01-01，2882 历元，同一份观测：
        「基础」档重复性 3.8 厘米（水平 1.8 / 高程 3.3）
        「完整」档重复性 4.5 厘米（水平 2.9 / 高程 3.5）
    **两者的解相差约 3.0 米**（三维 RMS）。

    👉 所以这几项**不是"可忽略的小量"**，是**米级**的东西。
       写"说不准"是诚实，但**已经知道了还写"说不准"就是过期** ——
       而过期的表现和"编一个数"一样：用户拿它做错的决定。

    ⚠️ **但"测得出来"不等于"测得准"**：上面这套数据**天线型号是空的**，
       而改正越细，天线模型不准带来的偏差越藏不住。
       **"更完整"不等于"更准"** —— 详见 `config.PROFILES` 里的说明。

### ⚠️ 潮汐改正有一个静默失效的开关组合

`tides` 下面 `enable` 是**总开关**，`solid`/`otl`/... 只管各自那一项算不算。
整个 Ginan 源码里 `enable` 只被用在一处（`src/cpp/pea/ppp_obs.cpp`）：

```cpp
if (recOpts.tideModels.enable)
    pppTides(COMMON_PPP_ARGS);
```

**所以 `solid: true` 配 `enable: false` = 一点改正都没有** ——
不报错、不警告、日志里也看不出来。实测过这个组合：结果和全关**一模一样**。

👉 **两个都得是 true。** 自检里专门有一条守这个
（`scripts/check_toolchain.py` 的「⑭」）。

### 固体潮为什么不要文件

| 它需要什么 | 从哪来 |
|---|---|
| 日、月位置 | 有 DE436 就用；**没有就退到 SOFA 的解析星历**（`planetPosEcef` → `jplEphPos` 失败则走 `iauEpv`/`iauMoon`） |
| 地球自转参数 | **本来就要下的** ERP 文件，不是为它多下的 |

所以它属于"零代价"那一类。

**实测**（ALIC 2026-09-02 整天，两份配置逐字节相同、只差这个 tides 块，
尺子是 IGc20 里的权威坐标）：

| | 3D | N | E | U |
|---|---|---|---|---|
| 关 | 9.5 cm | -0.1 | -5.5 | 7.8 |
| **开** | **7.7 cm** | -0.5 | -6.2 | **4.5** |

**垂直方向几乎减半，水平方向基本不动** ——
这正是固体潮该有的样子。改善落在物理上该改善的方向，
才说明这个数是它带来的，而不是两次跑之间的随机差异。

### 实测结果

```
$ pea --config reduced.yaml -n 60
Total processing duration : 00:00:03.56
→ ALIC_reduced_m05.POS            (93 行 = 头 + 60 历元)
→ ALIC_reduced_m05_smoothed.POS
→ ALIC_reduced_m05.TRACE          (3.1 MB)
```

前向解算的收敛过程正常（开头米级抖动，末尾稳定到 ~0.4 m）；
平滑解**不是**"收敛成单一值" —— 实测整天那份是**两段常数**
（同一天三次运行，分界在第 454 / 457 / 521 个历元，两段相差 7~9 厘米）。

⚠️ 所以它算出来的"重复性"会在 **0.0 和 2.9 厘米之间跳** ——
既不是常数，也不是精度。判据见 `posfile.repeatability_is_meaningful()`。

## 四、`--dry-run` 的真实语义（读源码 + 实测确认）

### ⚠️ 它的成功提示是**误导性**的

```cpp
void ACSConfig::sanityChecks() {
    sanityManager.runAllChecks(*this);   // ← 返回值被丢弃（函数返回 void）
}

bool pass = configure(argc, argv);       // ← pass 只来自 checkValidFiles
if (acsConfig.dry_run) {
    "Dry-run successful: configuration and sanity checks passed"   // ← 并不成立
}
```

**退出码 0 只保证两件事：**

1. ✅ YAML 能解析
2. ✅ 所有**声明的**输入文件都存在

**它完全不保证** sanity checker 通过。而且 6 个 checker 里有 **4 个会静默改写配置**
（只发 `warning` 级日志）：

- `EpochToleranceChecker` — 把 `epoch_tolerance` 砍成 `epoch_interval / 2`
- `IonosphericFreeComboChecker` — 强制关掉 `use_2nd_order` / `use_3rd_order`
- `RequiredSiteEccentricityChecker` — 强制打开偏心改正
- `SbasSanityChecker` — 只在 SBAS 模式下动

**推论**：`--dry-run` 之后**必须自己解析 warning 行**，否则用户永远不知道
配置被悄悄改过。**这是我们要补的第一层价值。**

### 日志级别的坑

| 参数 | 效果 |
|---|---|
| （默认） | 显示 info 及以上 |
| `-q` | 隐藏 **info**，**warning 仍然显示** |
| `-Q` | 隐藏 **warning**，只留 error |

要捕获 checker 警告，**用默认级别或 `-q`，绝对不能用 `-Q`**。

## 五、绝对路径能绕过一堆坑

`conditionalPrefix()` (`acsConfig.cpp`) 的规则是：
**路径含 `:`（Windows 盘符）或是绝对路径 → 原样返回，不加任何前缀。**

于是 `inputs_root` 和 `gnss_observations_root` 都可以直接写绝对路径：

```yaml
inputs_root: E:/Code/.../products/
gnss_observations:
  gnss_observations_root: E:/Code/.../data/
```

**这一条同时消掉了三个坑：**

| 坑 | 为什么不再是问题 |
|---|---|
| `exampleConfigs/{data,products,pea}` 是软链接，Windows 解压后变成 0 字节文件 | 根本不用它们 |
| "必须在 `exampleConfigs/` 目录里运行" | 路径是绝对的，CWD 在哪都行 |
| 不想往 `ginan-dist/source/` 里写东西 | 工作目录完全在别处 |

> **通用教训**：遇到一堆"环境要求"时，先找找有没有**一个配置项**能把它们一起消掉，
> 而不是逐个去满足。

## 六、四条取数路径

这是网络不可靠时的**降级设计**。四条路**同时存在**，不互相替代。

### 路径 ①：自动下载（首选）

按文件清单，从**多个候选源**里挑一个能用的，带断点续传和校验和。

### 路径 ②：代理后自动下载

用户开了代理（或填了代理地址），走同一条逻辑。
**网络诊断要明确告诉他：哪些源通了、哪些还需要代理。**

### 路径 ③：缓存复用

一次性文件（`igs20.atx` 等）下载后缓存到
`userdata/data/`（软件目录下），之后不再下载。
**下载过的东西不该再让用户等第二遍。**

### 路径 ④：手动提供（保险丝）

**这是最后一道保险 —— 任何网络环境下都必须走得通。**

用户自己在浏览器/别的机器/网盘上把文件搞到手，**全部丢进一个文件夹**，
agent 负责去里面找、认、搬到位。

```
<app_root>/inbox/          ← 用户往这里扔
    igs20.atx
    IGS0OPSRAP_20262450000_01D_15M_ORB.SP3.gz
    ALIC00AUS_R_20262450000_01D_30S_MO.crx.gz
    随便什么名字.zip
```

agent 要做四件事：

**① 扫描** —— 递归找出 inbox 里所有文件（不管名字、不管扩展名；
**但深度有上限，见下**）

> ⚠️ **2026-09-20 更正。** 这一行原来写的是「不管嵌套几层」——
> **那句话是假的**，而它一直假着。
>
> 实测：`MAX_DEPTH` 原来是 4，往下第 5 层的文件**完全看不见**，
> 而报告里**一个字都不提**。用户丢进来一个
> `data/{met,nav,obs}/…` 的文件夹（194 个文件），
> `scan()` 只看见 **21 个**，**173 个（89%）静默消失**。
>
> 边界还是"多套了一层分类文件夹"这种毫无道理的东西：
> `met/2026/244/`（4 层）活着，`obs/rinex2/2026/244/`（5 层）全没。
>
> 现在：上限提到 **8**（覆盖真实的镜像布局），而且**截断了必须报出来**
> —— 和 `too_big` 那条一个道理（**静默漏掉一个文件，比报错糟得多**）。
>
> 👉 「扫描」这件事现在由 `inbox.scan_detailed()` 负责，
> 它返回的 `ScanResult` 里带 `truncated` / `too_deep_files` / `depth_note`。

**② 识别** —— ⚠️ **靠内容嗅探，不靠文件名**。用户从浏览器下载可能得到
`igs20(1).atx`，从网盘同步可能得到 `新建文件夹/未命名.gz`。

| 类型 | 内容特征（读头几百字节） |
|---|---|
| ANTEX 天线 | 含 `ANTEX VERSION` |
| SP3 轨道 | 首行以 `#a` / `#c` / `#d` 开头 |
| CLK 钟差 | 含 `RINEX VERSION / TYPE` 且类型行为 `C` |
| ERP 地球定向 | 首行含 `version 2` |
| BRDC 广播星历 | 含 `NAVIGATION DATA` |
| RINEX 观测 | 含 `OBSERVATION DATA` |
| SINEX | 首行含 `%=SNX` |
| gzip 压缩包 | 魔数 `\x1f\x8b` → **先解开再嗅探** |

**③ 匹配** —— 和当前运行的文件清单对照：认出了哪些、还缺哪些。
**信息不全时不要猜** —— 认不出来就如实说"这个文件我没认出来，它是什么？"

**④ 复制** —— 往数据目录放一份**能用的**（按内容重新命名），**原件留在收件箱**，
并**报告动了什么**。

> ⚠️ **这一步原来是"搬运"（`shutil.move`，原件就没了），已改成"复制"** ——
> 文档字符串当年还特意写着"移动而不是复制（用户明确要的是『搬过去』）"。
> **用户后来把语义澄清了**：他要的是"东西到齐、能开始算"，
> 而"原件没了"是他没要求过的副作用。
>
> ⚠️ 改这个动作**带出了一个新的 bug**，值得记：原件还在
> → **同一个文件每次扫描都会被看到** → "再认领一次"不是跳过，
> 而是**又复制一份**，永远复下去。修法是幂等判断
> （内容相同就跳过，并说明"数据目录里已经有一份了"）。
> **改了数据的流向，就要重新想一遍所有依赖它的判断。**
>
> 复制仍然**不能覆盖**已有的同名文件（可能是用户特意放的另一份），
> 冲突时停下来问。

**目录位置可配置** —— 用户可以把它设成网盘同步目录，
这样"换台机器"时数据自动跟着走。

## 六点五、CrinEX（Hatanaka）：Ginan **读不了**它

> 实测日期：**2026-09-20**。

**结论**：CrinEX 编码的观测数据（`.crx` / `.crx.gz`）**不能喂给 Ginan**。

**出处**（Ginan 自己的文档，不是我们的推断）：

```
ginan-dist/source/src/cpp/common/acsConfigDocs.cpp:20
> The data should be uncompressed rinex (gunzipped,
> and not in hatanaka format), or RTCM3 formatted binary data.
```

**为什么这件事很容易踩**：CrinEX 的**头部是明文 RINEX** ——
`kind` 识别得出、`MARKER NAME` 也读得到，一路看起来完全正常。
只是观测数据段是 Hatanaka 编码。**人眼看不出来**（它是纯文本，不是二进制乱码）。

**我们怎么处理的**（2026-09-20）：

- 识别：`identify.FileIdentity.crinex` —— 判据是**头部里的显式标记**
  `COMPACT RINEX FORMAT`（实测 48 个真文件 48/48 命中，146 个反例 0 误判）。
  ⚠️ 原来的判据是"头部非打印字符 > 2%"—— **那个判据永远不会触发**，
  因为真 CrinEX 的非打印字符是 **0.00%**。
- 认领 / 下载：**拒绝**，并说清是 CrinEX。
  ⚠️ 拒绝而**不是**改名落盘 —— 落成 `.rnx` 的话 Ginan 会跑到一半才报错，
  而报错和真正原因（编码没解）离得很远；落成 `.crx` 的话它不匹配
  配置里的 `ALIC*.rnx`、**静默不参与解算**，用户看到的是"下载成功"。
- 解码：**没做**。要做得自己写（RNXCMP 的 `crx2rnx` 是 C，几万行）。
  ⚠️ PyPI 上的 `hatanaka` 包**不是纯 Python** —— 它 wheel 里直接打包了
  RNXCMP 的 C 二进制，还多带 `ncompress` 依赖。本项目不引捆绑二进制。

**实践含义**：从 CDDIS 等源下 RINEX 3，默认拿到的就是 `.crx.gz`。
要么换一个给明文 RINEX 的源，要么自己用 RNXCMP / GinanUI 转一份。
**GA 的 API 不受影响** —— 它的 `decompress=true`（默认）返回的是明文 RINEX。

### ⚠️ 那个 0.4 米**不是解算误差**，是文件头里的近似坐标

POS 里的 `dn/de/du` 是「历元位置 − 头里的 `APPROX POSITION XYZ`」。
（已核对：自己按 XYZ 差算一遍 NEU，和文件里那三列**逐位相同**。）

|---|---|---|---|
| ALIC / DARW / CEDU | 澳洲 | 0.430 / 0.434 / 0.431 m | 27° / 31° / 21° |
| BRUX | 欧亚 | 0.946 m | 45° |
| ALGO | 北美 | 0.141 m | 278° |
| GMSD | 日本 | 0.705 m | 125° |

三个**互相独立**的澳洲站，3D 只差 4 毫米、方位角只差 10° ——
这不是巧合，而是"同一块板块 + 同一个作业方"的共同特征。
**差异住在文件头那个坐标里，不在解里。**

⚠️ 这仍然只是**旁证**。判"准不准"必须拿**权威坐标**（IGS 的 SINEX 解）去比，
而这个程序**没有**下载"站坐标 SINEX"的能力 ——
所以它对"准不准"的回答只能是"不知道"，而不是一个数字。
**这是产品缺口，不是本次测量的结论。**

### 试过、但**没有用**的两条路（免得下一个人再试一遍）

| 试的 | 结果 | 为什么 |

```
ftp://igs.gnsswhu.cn/pub/gps/data/daily/<YYYY>/<DOY>/<YY>d/
```

### 实测数据（2026-09-24，2025-06-15 / DOY 166）

| 目录 | 内容 | 实测 |
|---|---|---|
| `.../2025/166/25d/` | **IGS 全球网观测** | **418 个站**，`.crx.gz`（**CrinEX**） |
| `.../2025/166/25o/` | 区域站观测 | **只有 9 个站**，但 `.rnx.gz`（**裸 RINEX 3.05**） |
| 同一天还有 | `25e 25f 25g 25h 25i 25l 25m 25n 25p 25q 25s` | 各字母是不同网络的子集（EUREF/导航/…）|

⚠️ **注意 `25d` 和 `25o` 的区别有两层**，不是一层：

    · `25o` = 区域网（9 站），但是**裸 RINEX**

「哪个字母有裸 RINEX」和「哪个字母有全球网」**不是同一件事** ——
要全球网就得解 CrinEX，要免解码就只有区域网。

### 速度实测（与 GA 对比，同一个站同一天）

| | 下载量 | 单连接速度 | 说明 |
|---|---|---|---|
| **武大 `25d`**（CrinEX）| **4.2 MB** | **173 KB/s** | 解压后 30 MB |
| GA（预签名 S3）| 30 MB（解压后）| **27 KB/s** | 无 Range、无 Content-Length |

**综合效率差约 40 倍**（体积 7 倍 × 速度 6.4 倍）。

⚠️ 而且武大还有 `MD5SUMS` / `SHA512SUMS` 文件 —— **可以校验下载完整性**。
   GA 那条路没有任何校验，只能靠内容判据（见 `download_testdata.verify_rinex`）。

### CrinEX 怎么解

**`FAST-main/src/fast/bin/crx2rnx.exe`**（FAST 自带）。

⚠️ **用法有个坑**：直接 `crx2rnx file.crx` 会报

    ERROR : invalid file name  .crx
    The extention of the input file name should be [.xxd].

—— 它要求输入文件名是 **RINEX 2 的 `.xxd` 形式**。RINEX 3 的 `.crx`
要用**管道**形式：

    cat file.crx | crx2rnx.exe - > file.rnx

✅ 实测（ABMF00GLP 2025-06-15）：4,181,263 字节 `.crx`
   → gunzip（10,101,555）
   → 管道解码得 **30,062,932 字节裸 RINEX 3.04**，`OBSERVATION DATA M`。

### ⚠️ 但 app **不能**直接捆这个二进制

`FAST-main/src/fast/bin/` 下的 `crx2rnx.exe` 是 **Cygwin 构建**
（旁边一整套 `cygwin1.dll`、`cygcore-*`、`cygz.dll`），
而 **Cygwin 运行时是 GPL**。这和 [ADR-001] 挡住 Ginan 二进制是同一条线。

所以对 app 来说，这是**一个待决策的设计问题**，三条路：

    ① 写一个纯 Python 的 CrinEX 解码器（项目原来评估过：几百行数值敏感的代码）
    ② 让 app 在**用户机器上找** crx2rnx（FAST/RNXCMP 装过就有），找不到就退回 GA
    ③ 继续用 GA（裸 RINEX、56 站、27 KB/s）

**在决定之前，下载脚本（开发工具，不随 app 分发）可以直接用 FAST 的那个二进制。**

## 七点五、POD 定轨：两个坑 + 一条我踩错的推论（2026-09-24 实测）

### ① `.NNi` 后缀是**歧义的** —— 可能是星历，也可能是电离层图

官方 POD 示例的数据目录里，三个"星历"文件的真面目：

| 文件 | 文件头第一行 | 真实类型 |
|---|---|---|
| `brdm1990.19p` | `NAVIGATION DATA     M (Mixed)` | ✅ 广播星历 |
| `codg1990.19i` | `IONOSPHERE MAPS     GNSS` | ❌ **IONEX 电离层图** |
| `emrg1990.19i` | `IONOSPHERE MAPS     GNSS` | ❌ **IONEX 电离层图** |

**症状**：Ginan 拿 IONEX 当广播星历解析 → **死循环**。

⚠️ 它的表现是「跑了 48 分钟没动静」，而三个指标共同指认它是**卡死**不是慢：

    · CPU      稳定 1.0 核（在烧，所以不像挂起）
    · 磁盘 I/O **冻结在 40.8 MB**，30 秒内零增长   ← **这一条是判据**
    · 内存     恒为 151 MB，一动不动

👉 **判据是 I/O 冻结**：真在算的话磁盘会继续读。（内存不涨也可能是流式加载，
   单看内存会误判。）

⚠️ **可靠判据是文件头第一行，不是后缀。** `identify.py` 把这两个文件判成
   `unknown`（置信度 `none`）—— **app 不会犯这个错**，错的是手写的取数脚本。

### ② 手写配置缺了 POD 的骨架 → 第 0 个历元 `dpotrf failed`

**同一份数据、同一个二进制、同一批先验产品，只有配置不同：**

| | 手写的配置 | 官方示例（**只改路径**） |
|---|---|---|
| `dpotrf (Cholesky) failed` | **1 次**（第 0 历元） | **0 次** |
| 第 1 个历元耗时 | **82 秒** | — |
| 稳定后每历元 | 崩溃 | **2.7 ~ 3.2 秒** |
| 产物 | 8 KB 空 SP3 | **SP3 85 KB / OBX 106 KB / CLK 322 KB，都在长** |

`build_config` 手写出来的配置，缺的是 POD 的**整块骨架**：

| 缺的整块 | 为什么致命 |
|---|---|
| `processing_options.minimum_constraints` | **基准定义**。POD 法方程没有它必然**秩亏** → `dpotrf failed` |
| `processing_options.orbit_propagation` | **卫星受力模型**：`integrator_time_step`、`egm_degree`、`central_force`、`ocean_tide`、`general_relativity`、`indirect_J2` |
| `processing_options.model_error_handling` | 整块（模糊度重置、剔除阈值） |
| `processing_options.spp.outlier_screening` | 整块 |
| `processing_options.gnss_general` | `pivot_receiver`、`minimise_sat_clock_offsets` |
| `estimation_parameters.global_models.eop` | 估地球定向参数 |
| `receiver_options.global.models.*` | 姿态 / 相位中心 / 潮汐 / 电离层分量… |
| `inputs.tides` `troposphere` `igrf_files` `planetary_ephemeris_files` | 那 8 个表**根本没进配置**（尽管 `Workflow.extra_inputs` 列了） |
| `outputs.orbex` `clocks` | 轨道 / 钟差产物 |

**反过来，手写的配置里还多出示例没有的键**（`emp_d_1`、`emp_b_2`、`apriori_position`、
`models.tides`）—— 示例里那些是**注释掉**的。

👉 **架构结论**：`build_config` 手写 200 个键，错一个就是「配置看着正常、跑起来是 NaN」。
   **官方示例本身就是模板** —— 载入它、只替换「文件在哪」那些键，
   才能让「对着官方示例逐条核」从人工清单变成**结构上不可能偏离**。

### ③ `OPENBLAS_NUM_THREADS=1` 把 POD 压成了**单核**（这一节改过三次，全部记下来）

**这一节本身就是一部"推 vs 量"的历史**，所以把三次都留着 ——
每一步都是前一步的更正，删掉中间那步就看不出为什么会错。

#### 第一次：说它把 Ginan 压成 1 线程 —— **观测是错的**

我报告「app 的 `pea_env()` 把 Ginan 从 20 线程压成 1 线程，浪费了 19 个核」。

| 环境变量 | 线程（**4 次观测全部在卡死状态下**） |
|---|---|
| 无 | 20 |
| `OPENBLAS_NUM_THREADS=1` | 1 |

#### 第二次：在正常解算的进程上重测 —— 线程数翻转，于是判断"没影响"

| 环境变量 | 线程 | 拆解 |
|---|---|---|
| 无 | **40** | Ginan 的 OMP 池 20 ＋ **OpenBLAS 自己的池 20** |
| `OPENBLAS_NUM_THREADS=1` | **21** | Ginan 的 OMP 池 20 ＋ OpenBLAS 的池 **0** |

⚠️ 卡死状态下 Ginan 还没进过任何并行区，OMP 池压根没建 ——
   那时看到的 20 个线程**是 OpenBLAS 的池**，我把它当成 Ginan 的了。

于是当时的结论是：`pea_env()` 按住的是 OpenBLAS 那个多余的池，
**「完全没碰 Ginan 自己的并行」**，保持现状。
（`acsConfig.hpp` grep `thread` = 0 命中 —— Ginan 配置里没有线程键，
 唯一的杠杆就是环境变量。）

⚠️ 但那一节**自己留了一句没做完的话**：
   「还没测的：40 线程 vs 21 线程在**不争抢**的情况下性能差多少。」

#### 第三次（2026-09-25）：量了**实际用掉几个核** —— 前两次都问错了问题

前两次数的都是**线程数**。线程数不等于在干活。
换一个判据（`TotalProcessorTime` 增量 ÷ 墙钟）直接量**占用核数**：

| `OPENBLAS_NUM_THREADS` | 进程线程数 | **实际占用核数** | 每历元【处理】耗时（87 站） |
|---|---|---|---|
| `1` | 21 | **1.01** | 20.6 / 19.7 / 18.6 / 18.4 → 69.6 / 77.3 / 79.5 秒 |
| 不设 | 40 | **8.32** | **12 / 11 / 12 / 12 → 43 / 43 / 44 / 45 秒** |

⚠️ 两条都是**同一份 87 站配置、同一天数据、同一台机器**
   （i5-14600KF，20 个逻辑核），差异只有那一个环境变量。**不设快 1.6~1.7 倍。**

⚠️⚠️ **21 线程那一列就是答案**：Ginan 那 20 个 OMP 线程**建了却没干活**。
   所以「完全没碰 Ginan 自己的并行」这句话，**在"线程存在"的意义上对，
   在"并行真的发生"的意义上是错的** —— 20 个核在旁边看着 1 个核跑。

👉 **结论（已落到代码）**：`pea_env()` **不再设任何线程变量**。
   用户的机器有多少核、该开多少线程，是库和 Ginan 的事，不是 app 的事。

   ⚠️ **连「按核数自动设置」也不做** —— 那是 app 替库去做库自己更清楚的决定，
      而用户换一台机器，这个决定就可能又错了。

   ⚠️ 而且不设的那一轮**没有出现 OpenBLAS 的挂起警告**。
      Ginan 内部本来就有 `ScopedOpenBlasThreadLimit`（`common/blasThreading.hpp`），
      只在它自己的 OpenMP 分块循环里限制 BLAS —— 那个保护精准得多，
      而原来那一刀把它连同全部并行一起砍掉了。

   改动的三处（缺一个就会一边改一边教用户做相反的事）：
   `environment.pea_env()` / `environment._check_threads()`（**已删**）/
   `diagnostics` 的 `openblas_threads` 规则（它原来照抄 OpenBLAS 自己那句话，
   让用户去设 `=1`）。守卫：`check_toolchain` ⑦d、`check_diagnostics` ④。

✅ **2026-09-29 补了「主动发现」（用户点的：「处理中如果发现只有一个 cpu
   工作的情况记得中断检查」）。** 上面那三处都是**被动**的 —— 它们只在
   `pea` 自己把 OpenBLAS 那句话打到 stdout 上时才起作用；而 1 核那件事
   **可能一声不吭**（当年就是跑了半天才发现）。

   现在 `runner.run_pea` 会在跑的过程中**采样占用核数**
   （`environment.process_cpu_seconds`：累计 CPU 秒 ÷ 墙钟；Windows 走
   `GetProcessTimes`，POSIX 读 `/proc`，**不引新依赖**），
   低于 1.5 个核、且机器本来有 ≥4 核时**报一句话**。

   ⚠️ **只报，不打断、也不替用户设环境变量** —— 一轮 POD 要几小时，
      光凭"核数少"就杀掉它是猜；而且那还是 app 替库做决定（见上）。
   ⚠️ 判据是**占用核数，不是线程数**：数线程会看到 40 个，
      而实际只有 1 个在干活 —— 这正是本小节的教训。
   守卫：`check_toolchain` ⑦f（**两个方向都测**：单核要报、多核不许报）。

⚠️ **87 站在 `OPENBLAS_NUM_THREADS=1` 下跑到第 7~8 个历元会卡住**
   （RTS 文件冻结、CPU 稳定烧 1.0 核 —— 和上面那个 IONEX 死循环的签名一样）。
   `ctor87`、`app_run` 两份历史日志的**最后三行**和现场逐字相同，
   都停在 `------- FILTERING BY CHUNK 1 --------`。

   ✅ **2026-09-27：换了线程设置之后不复现。**
   同一份 `ctor87` 配置、**不设任何线程变量**，平稳跑过了第 7、8、9、10 个历元
   （每个历元 103~106 秒，没有一次停顿）。

   ⚠️ **但"当年那 7 个历元到底是怎么停的"，仍然没有定论。**
      我试过一个解释——「是被超时杀掉的」——**算术上不成立**：
      1 个核时前面几历元约 20 秒、第 5 历元起约 75 秒，
      7 个历元总共才 5 分钟，够不着 60 分钟的超时线。
      ⇒ 所以那几份日志**究竟是卡住、被杀、还是别的原因，还是不知道**。
      确定下来的只有一件事：**现在这个设置下不卡。**

⚠️⚠️ **而判"卡住"用的那两个指标，有一个是不可靠的**（2026-09-25 当天就踩了）：

    **Network TRACE 的时间戳不是实时落盘的 —— 它会攒一批再写。**

    实测同一轮运行：先量到「8 个历元 / 3.5 分钟 = 26 秒/历元」，
    再量「38 个历元 / 180 秒 = 4.7 秒/历元」。**同一轮、相隔几分钟，差 5.5 倍。**
    长窗口（≥3 分钟）的两次数值彼此一致，短窗口的不可信。

    ⇒ **不能用短窗口读 TRACE 来判断"它是不是停住了"。**
      要判卡住，只能靠长窗口（几分钟）的**磁盘增长**，
      而且要和"这个历元正常要跑多久"比 —— 不能只看到 30 秒没长就下结论。

## 七点六、POD 的配置改成"官方示例当模板"（2026-09-24）

### 结论

`config.build_config` 原来是**手写**一份配置（照着 PPP 拼的）。对 PPP 能跑，
**对其他工作流是残的**：

| | 手写的 POD 配置 | 官方示例（只改路径） |
|---|---|---|
| `dpotrf (Cholesky) failed` | 第 0 个历元就失败 | **0 次** |
| 每历元 | 82 秒，然后 NaN 级联、崩 | **2.7 ~ 3.2 秒** |
| 产物 | 8 KB 空 SP3 | SP3 744 KB / OBX 952 KB / CLK 2.9 MB / SNX 224 KB |

**同一份数据、同一个二进制、同一批先验产品，只有配置不同。**

手写那份缺的是**整块骨架**：`minimum_constraints`（基准定义 —— 没有它法方程
**秩亏**，这就是 `dpotrf failed` 的来源）、`orbit_propagation`（卫星受力模型）、
`model_error_handling`、`spp.outlier_screening`、`gnss_general.*`、
`global_models.eop`、`receiver_options.global.models.*`、`inputs.{tides,troposphere}`…

👉 所以 POD 改成：**载入官方示例成 dict、只改文件路径和档位**。
   见 `ginan/examples.py` 和 `config._build_from_example`。

⚠️ 这**不是** `config.py` 模块 docstring 拒绝的"字符串模板"——
   那三条理由（静默漏替换 / 缩进改语义 / 无法静态检查）针对的都是**字符串**，
   对 `yaml.safe_load` 成 dict 的写法一条都不成立。

### 读源码得知的 5 条（**未实测**，出处见括号）

这五条决定了实现的样子。它们**没被实测**，是读 `ginan-dist/source/` 得来的 ——
用的时候要知道这一点。

1. **`include_yamls` 指向的文件不存在 ⇒ 硬失败**（`acsConfig.cpp:4659`）。
   官方 POD 示例引用 `products/boxwing.yaml`，而发行版里那个目录是没有的
   （上游是符号链接，Windows 解压后变成 0 字节残留）。
   ⇒ 那个键**必须删掉**，否则 pea 直接拒绝启动。

2. **配置里写的任何文件路径不存在 ⇒ `checkValidFiles` 硬失败**（`inputs.cpp:44-66`）。
   ⇒ 模板里的文件名必须被**替换**，绝不能留着当兜底。

3. ⚠️⚠️ **`egm_field: true` 但没有 EGM 文件 ⇒ 只打印一句
   `EGM data not initialised`，跳过最大的那一项受力，轨道照常输出**
   （`orbitProp.cpp:71-77`）。

   这是本项目最怕的那类失败：**看着正常、结果是错的**。
   ⇒ 所以 POD **只允许「完整」档**，而且缺 `EGM2008.gfc` 时**拒绝生成配置**
   （`ginan_tools.do_generate_config` 里那道门）。

4. ⚠️ **Ginan 对 `receiver_options.global.models.tides` 的默认值全是 `true`**
   （`acsConfig.hpp:1314-1320`），而 `pod_example.yaml` **没写这个块**。

   ⇒ "模板 + 删掉 `inputs.tides`"的结果是：**海潮改正开着、但模型文件没了、
     算不出来、不报错**。
   ⇒ 所以档位差量**必须把 `models.tides` 显式写成 false**，不能靠默认值。

5. **一个进程里只能有一个真实的配置来源** —— 这条是仓库的规矩
   （`check_recursion.py` 禁止函数自调用；`Workflow.example` 是"配置从哪来"
   的唯一判据，`build_config` 里只有那一个分支）。

#### ⚠️⚠️ 顺带量到的一条：**改线程设置**会让结果变，**重跑不会**

（2026-09-27 补测。同一份 46 站配置、同一份数据、同一台机器、跑满 288 历元。）

三份 SP3 逐历元比（8,928 条 = 31 星 × 288 历元，单位**米**）：

| 比的是哪两份 | 中位 | 99% | 最大 |
|---|---|---|---|
| **同设置重跑两次**（修后 vs 修后） | **0.0000** | **0.0000** | **0.000** |
| **修前 vs 修后**（1 个核 vs 8 个核） | **0.0323** | **1.5411** | **7.851** |

⚠️ 同设置那两份**除头部创建时间戳外逐字节相同**（`diff` 干净）。

⇒ 两条结论，**方向相反，都要记住**：

| | |
|---|---|
| ✅ **Ginan 本身是确定性的** | 同一份配置 + 同一份数据 + **同一份线程设置** ⇒ **逐字节复现**。[M6 复现包] 可以承诺这一点，**不必打折** |
| ⚠️⚠️ **但线程设置是结果的一部分** | 1 个核 → 8 个核，同一份配置的输出会变，**最大差到 7.85 米**（`PG30` 第 2 历元、`PG32` 第 9~11 历元），中位数 3.2 厘米、99% 1.54 米，超过 1 米的占 2.2% |

⚠️ 差别最大的那几条**全在开头十几个历元** —— 那时滤波器还没收敛、
状态协方差最大，并行归约的顺序差被放大。**这是解释，不是实测。**

⚠️⚠️ **对 ① 的验收数（2.39 米）的影响**：「我们的 2.40 vs 官方逐字跑的 2.29，
   差 5%」这个比较里，**两边的线程设置不一定相同** ——
   而这条实测说，光线程设置就能带来米级的差。
   ⇒ **5% 这个差不能当成"我们的配置有 5% 的偏差"**，
      它很可能就落在线程设置带来的散布里。

⚠️ 这条也**反过来**说明"修线程"那件事的代价：**快 2 倍，代价是输出变了**。
   不是"同样结果快一点"。**报性能提升的时候要一起说这句。**

⚠️ **2026-09-25 更正**：原表只有 39/87 两列，且写 39 站"2.1 秒/历元、

## 七点七、把死字段接上电的那一刻（2026-09-24）

这一条是**方法**，不是某个具体配置 —— 但它比大多数具体结论值钱。

### 发生了什么

`Workflow.needs` 是个**死字段**：`workflows.py` 的文档写着「用途：`plan_run`
按这个决定要下什么、`advise` 按这个说还缺什么」，而**全项目没有一处读它**。

（实测确认：把 `"bia"` 从 `pod.needs` 里去掉，**一点效果都没有**。）

于是把它接上：`catalog.plan_run(..., workflow=...)` 在末尾按 `needs` 筛一遍。

**接上电的那一刻，立刻暴露了两个洞：**

1. **`pod.needs` 里没写 `sp3`** —— 而 POD **需要** SP3（先验轨道，
   走 `pseudo_observations.sp3_inputs`，不是 `satellite_data.sp3_files`）。
   少了它，取数计划里没有先验轨道文件 → 配置里那一项为空 → Ginan 报缺文件。
2. **`ppp.needs` 和 `pod.needs` 哪个对**，没有任何东西能判断 ——
   因为从来没人拿它们和真实需求比过。

**⚠️ 那个 `sp3` 的洞在字段是死的期间一直存在，谁都不知道。**
改它没效果 → 没人看它 → 没人发现它写错了。**这是一个自洽的盲区。**

### 唯一能防住这个形状的办法

**把两个清单锁在一起，让它们必须同时改。**

    配置里**真正用到**的文件类别  ⊆  取数计划里会下的类别
    （反过来也查：计划里不许有配置一个字节都不用的类别 —— 那是白下）

判据从**配置本身**读出来（遍历生成的 dict，看哪些 `*_files` 键非空），
不从"我以为它要什么"读。守卫：
`check_toolchain.test_workflow_needs_covers_what_the_config_uses`。

⚠️ 那张 `键名 → 类别` 的映射表里有一条是关键的：

    "sp3_files"   → sp3      ← PPP 的轨道，当"已知位置"
    "sp3_inputs"  → sp3      ← POD 的轨道，当"观测值"

**同一类文件、两个位置。** 漏掉第二行的话，上面那个 `sp3` 的洞就依然测不出来。

### 可以推广的一句话

**一个"文档说它在用、代码里没人读"的字段，不是无害的遗留物 ——
它是一份没人核对过的声明。** 让它生效的时候，先假定它是错的。

## 七点八、下载下来的文件**被写多了**（2026-09-24）

### 现场

下 `EGM2008.gfc`（Ginan 桶里那个 72 MB 的重力场模型）时：

| | 字节 |
|---|---|
| 服务端说这文件多大 | **72,363,937** |
| 我们的 `.part` 下到 | **78,655,393** |
| 差 | **6,291,456 = 正好 6 MiB**（= 那次续传的起点） |

然后：

    zlib.error: Error -3 while decompressing data: invalid code lengths set
      ← gzip 解不开，文件是坏的
        ↓
    错误处理里 part.unlink()
        ↓
    PermissionError: [WinError 32] 另一个程序正在使用此文件
      ← 清理自己又炸了，**把真因整个盖掉**

用户和日志看到的是一条**文件被占用**的 traceback。真因（下下来的文件是坏的）
**一个字都没露出来**。

### 修掉的两个（都是静态确认的）

**① 完整性检查只查一个方向。**

```python
if total and written < total:      # ← 只查"少了"
```

那个多出 6 MiB 的文件**通过了**这道检查（78655393 > 72363937，不满足 `<`），
然后被交给 `_gunzip` 去炸。**一道"完整性检查"漏掉一个方向，就挡不住它存在的理由。**
现在两个方向都查，而且说得清是多了还是少了。

**② 清理失败会盖掉真正的错误。**

`_unlink_quietly()` —— Windows 上"删不掉"是**常态而不是意外**（杀毒、索引、
别的进程开着）。清理失败最坏就是占点磁盘，**不该改变这条记录说什么**。

⚠️ `missing_ok=True` 只挡 `FileNotFoundError`，**挡不住 `PermissionError`**——
这是两回事，别混成一个。同一个模式在 `fetch.py` 里有 **5 处**，全换成这个函数了。

### 没查清的那个（**如实记着，别当成已解决**）

**为什么正好多 6 MiB。**

算术上只有一个机制能同时解释"正好多 6 MiB"和"检查放它过去了"：

    服务端收了 Range、也回了 206，**但发的是整份文件**。
    而旧代码算总大小写的是 total = Content-Length + already ——
    服务端发的既是整份，这个加法就把 total 一起放大了，
    于是 written 和 total 同时多 6 MiB，**两边仍然相等**，检查看不出异常。

⚠️ **这个机制没有复现过。** 直连这台机器时服务端的 206 完全正常
（`Content-Range: bytes 54165504-72363936/72363937`，长度分毫不差）。

👉 但有两件事**与那个猜测成不成立无关，本身就该做**，所以做了：

    ① 206 **必须**带 `Content-Range`（RFC 要求），**总大小以它为准** ——
       不是"我们猜的起点 + 响应长度"
    ② 服务端从**别的位置**发的数据**当场拒绝** ——
       拼到 .part 后面只会得到一个坏文件

### 查过、排除了的（免得下一个人重查一遍）

| 怀疑 | 结果 |
|---|---|
| 服务端 Range 处理有问题 | ❌ 正常（206 + 正确的 `Content-Range`） |
| 下载是并发的（两个线程写同一个 `.part`） | ❌ 不是，`fetch_plan` 是顺序 for 循环 |
| `identify` 泄漏文件句柄（导致 unlink 失败） | ❌ 不泄漏（CPython 引用计数当场就关） |
| 续传逻辑本身坏了 | ❌ **不是** —— 受控实验：手工把 `.part` 截到 800,000 字节，续传后落盘 11,357,406 字节，**和没截断时逐字节一致** |

### 顺带暴露的：**夹具不贴真实**

`check_files.py` ⑧ 那个断点续传的假服务端，回的 206 **只有 `Content-Length`、
没有 `Content-Range`** —— 那在 HTTP 上是不存在的响应（RFC 要求 206 必须带）。

于是那两条路**一个守卫都没有**：「服务端从别处发的」「总大小该以 Content-Range 为准」。
加上核对续传起点那个修复之后它才露出来。

👉 **夹具不贴真实，那条路的 bug 就没有守卫。** 这次是反过来：
**修复逼着夹具变得真实。**

### ⚠️ Ginan 在 Windows 上的一个缺陷：SP3 的历元标记是 `E*`

**不是我们的代码**，记下来是因为它会让下一个做比对的人卡住很久。

现象：Ginan 写出来的 SP3，**第 2 个历元起的行首是 `E*` 而不是 `*`**
（288 个历元里 287 个）。而 Ginan 自己的读取端（`sp3.cpp:76`）只认 `buff[0] == '*'`
—— 于是**它读自己的产物，只能读到第 1 个历元**，其余位置行全挂到那个历元上。

机制（源码闭环）：

    sp3Write.cpp:294   sp3Stream.seekp(-4, std::ios::end);   // 注释写"回到 EOF\n 之前"
    sp3Write.cpp:266   std::fstream sp3Stream(filename);     // ← 默认文本模式，没有 ios::binary

Windows 文本模式把 `\n` 写成 `\r\n`，所以磁盘上 `EOF` 后面是 **5 字节**
（`E O F \r \n`），而 `-4` 假设 4 字节 —— 写指针落在 `O` 上，晚了一个字节：

    ... E   O   F  \r  \n        seekp(-4) 落在 O
         ↑   ↑
      没盖到  写 "*" 盖这里        →  生成 "E*"

**那个 `E` 是 `EOF` 的第一个字母没被盖掉。**

实测影响：拿刚跑出来的 POD 产物去做比对，**190 个历元全部「not found」**；
把 `E*` 改成 `*` 之后 **190 → 0**。

⚠️ **官方示例的输出也是 287 个 `E*`** —— 所以这是 Windows 上**所有** Ginan SP3
产物都有的，不是我们这批特有的。

⚠️ **本项目的决定：不改 Ginan**（那是上游的事）。但要知道：
   **app 交给用户的轨道文件，标准 SP3 读取器读不全。**

- 没试过 `slr_pod_with_pseudoobs_gal.yaml`（Galileo 那条路）。

## 七点十一、⚠️⚠️ SP3 默认文件名**在 Windows 上会让产物静默消失**（2026-09-25）

**这是这一轮挖到的最要命的一条** —— 它让「跑完了但什么都没有」看起来像"配置没开"。

### 机制

```cpp
// ginan-dist/source/src/cpp/common/acsConfig.hpp:329
string sp3_filename = "<SP3_DIRECTORY>/<CONFIG>-<LOGTIME>_<SYS>-Filt.sp3";

// ginan-dist/source/src/cpp/pea/outputs.cpp:106
replaceString(str, "<LOGTIME>", "<YYYY>-<MM>-<DD>_<HH>:<mm>", false);
```

`<LOGTIME>` 展开后**中间带一个冒号**（`2019-02-14_10:12`）。
**Windows 文件名不允许 `:`** ⇒ 文件创建失败，**而没有任何错误信息**。

**实测**：LEO 官方示例整天跑完（8640 历元、`PEA finished`、退出码 0），
`out/` 里**一个 `.SP3` 都没有**。加上一行显式文件名之后：

```yaml
outputs:
  sp3:
    filename: <CONFIG>_<YYYY><DDD><HH>.SP3     # ← 不含 <LOGTIME>
```

**立刻产出 22,664,929 字节的 SP3。**

### 为什么 POD 没踩到

| 配置 | sp3 文件名 | 有产物？ |
|---|---|---|
| 官方 **POD** 示例 | `<CONFIG>_<YYYY><DDD><HH>.SP3`（**不含 `<LOGTIME>`**） | ✅ |
| 官方 **LEO** 示例 | 没写 `filename` ⇒ 用默认值 | ❌ **Windows 上静默无产物** |
| 官方 **SLR** 示例 | 没写 `filename` ⇒ 用默认值 | ❌ 同上 |
| **app 生成的 POD 配置** | `20250615_202516600.SP3`（完全显式） | ✅ **免疫** |

⇒ **app 必须在所有工作流里都写显式 sp3 文件名**，绝不能依赖默认值。
   （POD 那条已经写了 —— 那是运气，不是设计。）

### 判据（免得下次又当成"配置没开"）

    · 日志里有 `Warning: Writing SP3 file, failed to get data for satellite …`
      ⇒ **说明 SP3 写入被调用了**，问题不在配置开关上
    · `out/` 里没有 .SP3、也没有任何报错 ⇒ 先怀疑**文件名**
    · 找文件名模板：`acsConfig.hpp` 的 `sp3_filename` 默认值 + `outputs.cpp:106` 的展开

⚠️ **这一条和 `E*`（七点九）是两个独立的 Windows 缺陷**，别混。
   `E*` 是**写出来的文件读不回去**；这一条是**文件根本写不出来**。
   两条都源自「Windows 和 Linux 的差异没被考虑」。

## 七点十二、⚠️⚠️ 轨道先验值的**参考系**：配置里给的必须是 **ECI**（2026-09-25）

**这是 LEO 定轨那条 11.6 万米级错误的根因**，而且它是个**会静默给出错轨道**的坑。

### 现场

`LEO_dynPOD.yaml` 里 `estimation_parameters.receivers.L64.orbit.apriori_value`
给的是 `[5618061.478891041, 2452804.124419954, -3139258.743281315, …]`
—— **这正好等于参考 SP3（ECEF）里第 1 历元的坐标**。

跑出来的轨道离参考 **11,646 公里**。而几何特征很特别：

> ⚠️ **「11,646」是当时那一轮的现场，而那一份配置没有留档。**
>    2026-09-27 拿留档的 `leo_eci_apriori` 重测是 **7,283.2 公里**（下面的表）。
>    两个数都是"绕 Z 转"的同一件事，只是**转角不同** ——
>    **别把 11,646 当现在的数用。**

    · Z 分量几乎相同（-3129 vs -3139）
    · XY 平面的**模**几乎相同（6135 vs 6130）
    · ⇒ 这是**绕 Z 轴旋转**的特征，不是另一条轨道

算了一下转角：**实测 143.43°**，而 **2019-02-14 00:00 UT 的 GMST = 143.73°**。
**差 0.30°。** ⇒ 整条轨道被转了**整整一个地球自转角**。

### 根因（源码闭环）

```cpp
// navigation.hpp:52  —— 状态的类型是 ECI
VectorEci aprioriPos;      ///< Inertial satellite position at epoch time

// 已有的两处赋值**都显式转换**
compare.cpp:175   satNav.aprioriPos = frameSwapper(peph0.pos);   // ECEF → ECI
debug.cpp:113     satNav.aprioriPos = frameSwapper(ecef);        // ECEF → ECI

// 而配置里的 apriori_value **原样赋进去，不做转换**
// algebra.cpp:3957
init.x = kalmanModel.apriori_value[index];
```

⇒ **配置里写的 `apriori_value` 被当成 ECI 用。** 而 LEO 示例给的是 ECEF。

### 修法（实测有效）

把先验按 `Rz(+GMST)` 转到 ECI 再填进配置：

    r_eci = Rz(+θ) · r_ecef            θ = GMST
    v_eci = Rz(+θ) · (v_ecef + ω × r_ecef)      ω = 7.2921151467e-5 rad/s

⚠️ 注意方向：`Rz(+θ)`，不是 `Rz(−θ)`（我先写反了一次，看起来"变好了"所以差点当成成功）。

#### ⚠️⚠️ 这一节的数**改过一次** —— 原来的对不上，记下来

本节原来写的是 **「11,646 公里 → 35 公里」**。2026-09-27 拿着满盘产物重算，
**那两个数一个都复现不出来**。可复现的是这组（`leo_exp/cmp_leo.py`，逐历元对参考轨道）：

| 配置 | t0 差 | 600 历元中位差 |
|---|---|---|
| 转反了（`leo_eci_apriori`） | **7,283.2 km** | 9,054.2 km |
| 转"对"了但 **GMST 差一天**（`leo_eci_plus`） | **73.5 km** | 9,054.2 km |
| GMST 也取对（`leo_eci_plus2`） | **35.3 km** | 9,054.2 km |

> ⚠️ 「11,646」那个数**不是错的**，是**另一个量**：它等于
> `配置里写的先验值` 到 `参考轨道 t0`（ECEF）的距离（实算 11,651.3 km）。
> 而"产物 t0 到参考 t0"是 7,283.2 km —— Ginan 会在写产物时再转一次系，
> 所以**这两个量差着一整个 GMST**。
> **把前者当后者写进结论，就是这一节的错。**

⇒ 教训和七点十九那条一样：**报数之前先说清"这是哪两个东西之间的距离"**。

### ⚠️ 但这只解决了一半 —— 剩下的还没解决（完整版见七点十九）

修完先验系之后，**误差仍然一路涨**（下表是 `leo_eci_plus`，GMST 差一天那一版）：

| 历元 | 距参考 |
|---|---|
| #0 | 73.5 km（GMST 取对之后是 **35.3**） |
| #50 | 39.2 km |
| #100 | 250.4 km |
| #150 | 7,040.1 km |

把**经验加速度**关掉（`emp_r_0/emp_t_0/emp_n_0` 的 `estimated: [false]`）之后：

    · 半径不再炸（6865~6907 km，物理上正常）
    · 但位置仍漂到几千公里

⇒ **还有第三个原因没找到。** 到此为止已确认的是：
   ① 先验参考系（已修，t0 35.3 km）
   ② 经验加速度会让轨道发散（关掉能止住发散，但不是完整解法）

> 👉 **第三个原因在 2026-09-27 找到了，而且它不是"力模型"** ——
>    是**观测对轨道的约束几乎为零**，"轨道"基本是积分器推出来的。
>    完整版、十一种改法的对照表、以及**我在那里量错的 1000 倍单位**，
>    都在 **七点十九**。**这一节到此为止，往下看它。**

### ⚠️ 对本项目的影响

**app 的 GNSS POD 工作流不受这条影响** —— 它的 `estimation_parameters.satellites.global.orbit`
里**没有 `apriori_value`**，先验来自 SP3 输入文件，走的是
`satNav.aprioriPos = frameSwapper(...)` 那条**已经转过**的路。
⇒ 只有「在配置里手写轨道先验值」的工作流会踩到（目前只有 LEO 那两条示例）。

### 顺带记下的另外三条（同一批实验里发现的）

| | |
|---|---|
| **SP3 头部写的历元间隔是错的** | LEO 输出实际 10 秒一个历元，头部却写 `1.00000000`。Ginan 写的是"请求的"间隔（默认 1），不是实际间隔 |
| **LEO 示例的天线/接收机型号是占位符** | `antenna_type: "ANTTYPE"` / `receiver_type: "TRIG"` —— 两个 LEO 示例里都这么写。每个历元报一次 `ERROR radome2none(): string length is less then 20 characters`（实测 8640 次） |
| **参考 SP3 自己也不自洽** | `GNI1B_2019-02-14_C_04.sp3` 头部写 `L64`、**数据行却是 `PG01`**。注释说它是 `GrccOrbit2Sp3.py` 转换来给 `leoOrbValidation.py` 用的，而那两个脚本**不随源码发布** |
| **示例的 AOD1B 解混频文件是别的日期** | 引用的三个文件是 **02-18/19/20**，而观测和处理的是 **02-14**。桶里**也只有那三天**，拿不到 02-14 的。（实测把那三个文件去掉、`aod: false`，结果**没变化** —— 所以它不是发散的原因） |

### ⚠️ 一条我说错了的（记下来免得下一个人重推）

我一度报告「**`apriori_value` 里的速度被忽略了**」—— 依据是「两份只差速度的配置，
跑出来 #60 的距离都是 188206.2」。**那个结论是错的。**

**错在哪：我比的是一个四舍五入到 0.1 的数字，不是文件。** 那时两边都已经发散到
差不多的状态，那一位数字恰好相同 —— 于是我把「恰好相同」读成了「完全没影响」。

**逐字节比两份输出**（各跑 90 秒）：

    leo_eci2.SP3  md5=1958d74062d5    leo_eci3.SP3  md5=ce9beff95fde   ← 不同
    第 1 条 L64 位置一样（都是起点），**第 2 条起就分开了**（5566.8 vs 5570.4）

源码也对得上：`ppp_obs.cpp:2159` 确实把 `velInit`（读 `apriori_value[i+3]`）加进了滤波器。

👉 **教训**：`cmp -s` 或者 md5，别拿一个打印出来的数字当"逐位相同"。

## 七点十三、⚠️⚠️ `epoch_control.end_epoch` **完全不起作用**（2026-09-27 实测）

### 结论先说

**配置里的 `end_epoch` 不会让 Ginan 停下来。** 唯一能刹住历元循环的
是**命令行参数** `-n <N>`（`max_epochs`）。

### 现场

官方 `brdc2sp3.yml` 写着 `end_epoch: 2019-07-18 23:45:00`，配置摘要里也
**明明打印了**这一行（`epoch end: 2019-Jul-18 23:45:00`）。照它跑：

    跑到我手动杀掉：**100,407 个历元**、到 **2022-05-28**、
    **1036 个 SP3 共 1.9 GB**（从 2019-07-18 一路到 2022-05-20）

### 对照实验（`ginan-testdata-202506/cheap3/probe_end_epoch.py`，三条各 120 秒上限）

| | `end_epoch` | `-n` | 结果 |
|---|---|---|---|
| A | `01:00:00` | — | ❌ 超时，**17,794** 个历元 |
| B | `01:00:00` | `5` | ✅ 退出码 0，`Exiting at epoch 5 as epoch count 5 has been reached` |
| C | 无 | 无 | ❌ 超时，**24,455** 个历元 |

### ⚠️ 而 PPP/POD 一直没暴露这件事

它们之所以看着正常，是因为**观测文件到当天为止就没了**：

    官方 POD 的日志：`Processed epoch #288 … 23:55` → `Inputs finished at epoch #289`

`main.cpp:1211-1226`：所有输入流读完之后 `complete = true`，外层的
`while (complete == false)` 才退出。**那是"恰好"，不是"配置管住了"。**

⇒ 任何**没有观测**的工作流就没有这个恰好。`brdc2sp3` 就是。

### 代码上为什么没兜住

`main.cpp:939-981` 的 `atLastEpoch()` 里**确实有**那个判断：

    if (acsConfig.end_epoch.is_not_a_date_time() == false &&
        tsync.to_posixTime() >= acsConfig.end_epoch)   → return true

而配置摘要也是从 `acsConfig.end_epoch` 打印的（`acsConfig.cpp:1501`），
所以值**读进去了**。但 100,407 个历元里它一次都没返回 true。
**根因没查**（用户的指示是"官方软件的问题不管"）——
本项目需要的是**知道它不可靠**，不是修它。

### 判据（免得下次又当成"跑得很慢"）

| | |
|---|---|
| ✅ 看**退出码和产物数**，不要只看"还在不在跑" | `-n` 生效时日志里有一句 `Exiting at epoch N as epoch count N has been reached` |
| ✅ 产物**个数**是第一个信号 | 一份跑对了的 `brdc2sp3` 一天只出 **1 个** `.sp3`；失控时每个历元一个文件 |
| ⚠️ `-n` 是 `epochs - 1` 那句 | `max_epochs` 的判断（`main.cpp:942`）排在 "Processed epoch #" 那句（`main.cpp:959`）**前面**，所以最后一个历元不打印 |

### 对本项目的影响

`config.epoch_count(inp)` 算出来的数会**总是**传给 `-n`（见
`ginan_tools.do_run_processing`）。配置里的 `end_epoch` 仍然写（它描述意图），
但**绝不依赖它** —— 守卫 ⑲a 锁住这一点。

## 七点十四、⚠️⚠️ Ginan **读不懂自己写的** SP3（2026-09-27 实测）

### 结论先说

Ginan 在 Windows 上写的 SP3，**第 2 个历元起的行首是 `E*` 而不是 `*`**。
而它的 SP3 读取器只认 `*` ⇒ **它读自己的产物只读到第 1 个历元。**

### 现场

`brdc2sp3` 跑出的一天（96 历元、半径 26,473 km、**内容是对的**）
拿去和 IGS 精密轨道（`TUG0R03FIN_..._ORB.SP3`）比：

| | 公共历元 | 3D 残差（去 Helmert） |
|---|---|---|
| 直接比 | **1** | 1,800,000 米 |
| 把 95 个 `E*` 修成 `*` 之后再比 | **96** | 中位数 **1.092 米**；汇总行 **1.319809 米** |

⚠️ **1.1 米正是广播星历该有的量级** ⇒ 产物本身没问题，`E*` 是**唯一**的原因。
（不是推的：修一处、变一处，其余条件不变。）

### 逐字节的现场

    #dV2019  7 18  0  0  0.00000000      96 ORBIT igb14 FIT  GAA^M$
    ## 2062 345600.00000000   900.00000000 58682 0.0000000000000^M$
    +  157   G01G02…
    *  2019  7 18  0  0  0.00000000          ← 第 1 个历元：正常
    …
    E*  2019  7 18  0 15  0.00000000         ← 第 2 个起：坏

⚠️ `cat -A` 里的 `^M$` 说明这份文件是 **CRLF** —— 正是七点九那个
`seekp(-4)` 缺陷的现场（`sp3Write.cpp:294` 假设 `EOF\n` 是 4 字节）。

### ⚠️ 这不是新发现的缺陷，但一直没人修

`ginan-facts.md` 七点九早记着根因。但**全项目搜 `E*`：0 命中** ——
app 里一处都没有修。① 的 POD 验收是**手工**修了文件才比出来的
（`orbitcheck/cmp3.yaml` 用的是 `ours_fixed.SP3`）。

⚠️ **这条对 `compare_orbits` 是致命的**：比对工具最常见的用法就是
"拿我的轨道和 IGS 比"，而被比的那份多半是**我们自己的产物**。
不修的话报出来的是"1 个历元 / 1,800,000 米" —— 一个**看着像结果**的垃圾数。

### 修法（app 侧，不动 Ginan）

`ginan/sp3file.py`：

    repair_epoch_tags(text) -> (text, n)   # 行首 `E*` → `*`
    repair_file(src, dst) -> n             # 读写都用 newline=""（保住 CRLF）

⚠️ **行首锚 `(?m)^E\*` 是必须的** —— 但要说清它保的是什么：

    实测对 30287 行的一份真产物：`E\*` 命中 95、`(?m)^E\*` 也命中 95，**差 0**。

⇒ **在真产物上锚不锚结果一样**（数据行是 `PG01`/`VE01`，`E` 后面跟数字不是 `*`）。
   所以不能声称"不锚就会毁掉数据行"。真正承重的是 **SP3 的 `/* … */` 注释行**
   （格式里是自由文本，我们自己的产物里就有 4 行）—— 守卫 ⑲d 的夹具里
   **刻意放了一条带 `E*` 的注释行**，否则那条守卫永远变不了红。

### 顺带量到的两条

- 头部那个数（`#dV2019 … 96 ORBIT`）**是历元数**，不是别的 ——
  而**同一行里的 `igb14`（参考框架名）里有数字 `14`**。
  拿"把所有数字抠出来取最后一个"当解析会算出 **14**，而且**不报错**。
  本项目的解析用结构化正则（`sp3file._SP3_HEAD`）。
- 间隔在 `##` 行的**第 3 个字段**：Ginan 写 `900.00000000`，
  TUG 写 `300.00000000`，IGS 写 `900.00000000` —— 都是浮点，不是整数。

## 七点十八、⚠️⚠️ 官方 `fit_sp3_pseudoobs.yaml` 的 SP3 产物是**惯性系**（2026-09-27 实测）

### 结论先说

`fit_sp3_pseudoobs.yaml` 的 `outputs.sp3` 里写着 **`output_inertial: true`**。
照它跑出来的 SP3，坐标是**惯性系**的，而 SP3 是**通用交换格式** ——
IGS 自己的、app 的 `compare_orbits`、任何第三方工具，**都按地固系读它**。

⇒ 拿它去和 IGS 的 SP3 比，得到的是 **31,863 公里**的"差异"。

⚠️ 而它**看着像结果**：同一个历元、同一批卫星、报告"32 颗卫星 96 个公共历元"，
三个方向的分量（N/R/T）都算得出来 —— 只有一个数字离谱。

### 隔离实验（**只改这一个开关**，其余全同，`-n 288`）

| 配置 | SP3 头部 | `PG01` 前三个数 |
|---|---|---|
| `output_inertial: true`（= 官方示例） | `#dV` | `  8501.71  13507.40  21222.43` ← **惯性系** |
| `output_inertial: false` | `#dV` | **`-14420.35   6772.84  21243.88`** ← 地固系 ✅ |

两次的 `output_velocities` **都保持 `true`**，所以变的只有坐标系这一件事。

⚠️ **两份的模长一样**（都 ≈26,560 km）、**钟差一模一样**（`291.454625`）
—— 是**转了个坐标系**，不是算错了。

### ⚠️ 顺带隔离的：`output_velocities` **无害**

## 七点十九、⚠️⚠️ LEO 定轨：**先验值转反了 74 度**，而"轨道"其实是积分器推的（2026-09-27 实测）

> 路线图 ③ 原来记的是「能跑完，但轨道还不对」，三个原因里找到两个，
> **第三个没找到**。这一轮把第三个找到了，而且它不是"力模型"的问题。

### ① 先验值的参考系：**转反了**

`estimation_parameters.receivers.L64.orbit.apriori_value` 是 6 个数（位置 3 + 速度 3）。

| | |
|---|---|
| **官方示例给的值** | `5618061.479, 2452804.124, -3139258.743` |
| **参考轨道 `GNI1B_…sp3` 的第一行** | `5618.061479, 2452.804124, -3139.258743`（km） |

⇒ **逐位相同** ⇒ 官方示例给的是 **ECEF**（SP3 天生是地固系）。

而 Ginan 要的是 **ECI**。实测（`产物 t0 的角度 = 先验值的角度 − GMST`）：

    参考(ECEF) t0 角度   23.59°
    配置 apriori 角度   239.86°
    产物 t0 角度         96.50°
    GMST(2019-02-14 00:00) = 143.7290°   ← 标准公式算出来的真值
    （这一段原来写 142.74°，**那是 2019-02-13 的 GMST** —— 差一整天，见下）

    239.86 − 142.74 = 97.12 ≈ 96.50 ✅   ⇒ Ginan 把先验值**减去** GMST

⇒ 所以正确的先验值 = ECEF **绕 Z 加** GMST（不是减）。
   而仓库里那份 `leo_eci_apriori.yaml` 用的是 **减** —— 实测它的方位角 **239.86°**，
   正好等于 `ECEF 方位角 23.59° − GMST`（差约 1°）⇒ 产物 t0 落在离参考
   **7,283.2 公里**的地方（逐历元比，见下面那张表）。

⚠️ 这一段的旧版把「配置值离参考 **11,651 公里**」（实算 11,651.3，是真的）
   当成了**产物**离参考的距离，又由它推出「差了 2 × 74° → t0 差 11,651 公里」。
   **两个量差着一整个 GMST**，见本节开头那段更正。

**本节原来写的"改正后的值"**（GMST = 142.7434° —— ⚠️ **这个值是错的，往下看**）：

    位置  -5956488.1067   1448831.3524   -3139258.743
    速度      3226.4207     -1405.0257       -6762.167

> ⚠️⚠️ **这个值本身是错的 —— 它用的 GMST 差了一整天。**
>    `142.7434°` 是 **2019-02-13** 00:00 的 GMST；
>    2019-02-14 00:00 的**标准值**（IAU 1982 / Vallado）是 **143.7290°**。
>    两者差 **0.9856°** —— 正好是地球一天转过的角度（360/365.25 = 0.9856）。
>
>    ⇒ 用 `143.7290°` 重算是（位置 / 速度）：
>
>        位置  -5980529.1204   1346155.3749   -3139258.7433
>        速度      3250.1119     -1349.3179       -6762.1668
>
>    ⚠️ 而实验目录里那两份 `leo_eci2.yaml` / `leo_eci3.yaml`
>       **用的就是这个值**（和我重算的只差 **9 厘米**）——
>       也就是说**当时算对过**，后来写这一节时又退回了差一天的那个。
>
>    ⚠️ **Ginan 自己也不是完全准的**：从产物量出它实际用掉的转角是
>       **143.4206°**，比标准值小 **0.31°** —— 换一个完全正确的先验值，
>       仍然会剩这么一点。所以**残余不会是零**。

⚠️ **速度不是单纯旋转**：`v_eci = Rz(+GMST)·v_ecef + ω × r_eci`
   （`ω = 7.2921151467e-5`）。实测：只转不加速度项的话 |v| 会对不上
   （旋转保模长，而这里 7600.8 → 7623.0 m/s）。

**效果（和参考轨道逐历元比）**：

| 配置 | 用的 GMST | **t0 差** | 中位差（600 历元） |
|---|---|---|---|
| 转反了（`leo_eci_apriori`） | ——（减了一个 GMST） | **7,283.2 km** | 9,054 km |
| 转对了，但**差一天**（`leo_eci_plus`） | 142.7434°（= 02-13 的） | **73.5 km** | 9,054 km |
| **转对了 + GMST 也对**（`leo_eci_plus2`） | **143.7290°** | **35.3 km** | 9,054 km |

⚠️ **修 GMST 把起步误差砍掉一半**（73.5 → 35.3），**长跑的中位数还是那个 9,054**。

⚠️ 剩下那 35.3 公里**正好对得上 Ginan 自己的转角偏差**：
   0.31° 的弦长 = `2 × 6887.2 × sin(0.155°)` = **37.3 km**，实测 35.3 km。
   ⇒ **解释（拟合，不是实测）**：残余已经不再是"我们填错了"，
     而是 **Ginan 内部那次旋转本身就差 0.31°**。
     要证实得进它的源码 —— 被 ADR-010 挡住。

⚠️⚠️ **只改了起步那一下 —— 长跑的中位数一模一样。**
   因为后面那 9,000 公里是**积分器漂的**（见 ②），和先验值无关。

⚠️ 而且那个"**瞬时掉到 4679 公里**"的假故障**也一起没了** ——
   它其实就是滤波器从错先验慢慢收敛的过程。

⚠️ **对照：先验值确实在被用。** 把正确的值再偏 **+100 km**（`p_shift`）
   ⇒ t0 差 **140.8 km**（≈ 100 km + 原有的 40 km）✅

### ② ⚠️⚠️ 观测对轨道的贡献**几乎为零** —— "轨道"基本是积分器推的

改完先验值以后轨迹看着不错，但**轨道状态的 sigma 在一直涨**：

    sigma: [1, 1, 1, 0.1, 0.1, 0.1]，process_noise: [0]

没有观测更新时，位置 sigma 应该按 `sqrt(σ_x² + (σ_v·Δt)²)` 涨。
实测（Δt = 10 秒、σ_v = 0.1 m/s）：

    历元       0      1      2      3      4      5 ...    19
    σ 实测   0.79   1.28   2.15   3.10   4.08   5.07      19.16
    σ 自由积分  —    1.414  2.236  3.162  4.123  5.099      19.03

⚠️ **几乎逐历元重合**（前几个历元略低一点 ⇒ 确实有一点点更新），
   到第 19 个历元实测反而略高于自由积分。
   跑到 120 个历元时 σ 已经是 **1.0876e8 米**（10.9 万公里）。

⚠️⚠️ **但"零更新"这个说法是错的**（我第一版就是这么写的，后来查了状态 dump 才改）：
   `+STATES/PPP` 那一行还有一列 **`Adjust`**，实测它是**非零**的
   （0.406、1.253、5.174、…）⇒ 状态**每个历元都在被调**。

⇒ 准确的判据是：**更新弱到几乎不起作用**（σ 的轨迹和自由积分几乎重合），
   **不是"完全没有更新"**。

⇒ 所以那份"轨道"基本是**数值积分器把先验值一路推出来的**。
   它和参考轨道差 **9,054 公里**。

⚠️ 而且这是**自我强化**的：σ 一旦涨过 `postfit.state_sigma_threshold: 4`，
   测量会被大量剔掉 ⇒ σ 涨得更快 ⇒ LEO 从产物里**消失**。

## 七点二十一、武大的**观测数据**（第三种接口）+ 一个 44 倍的差距（2026-09-29 实测）

### 结论先说

| | |
|---|---|
| **武大有观测数据** | ⚠️ 本文件以前写的是「**GA 是唯一给观测的源**」—— **那句话是错的** |
| 用的是**第三个清单接口** | `obsList` —— 和产品的 `jmxlList` / `gbxlList` **不是一回事**，它**必须带站号**（`site` 是**数组**，传字符串等于没传） |
| 覆盖 | 26 个站的样本里 **21 个有**，其中 **9 个是 GA 没有的**（WUH2 / URUM / GMSD / MIZU / ABPO / NKLG / SOLO / THTI / MAL2） |
| 拿到的是什么 | 长名 `.crx.gz`（RINEX 3 + CrinEX）—— **本程序的 `crinex.py` 能解**，整条链已经验过 |

⚠️ `gs` 只有两个取值，实测：`d` = 21/26 个站有；**`o` = 只有 2 个站**，
   而且全是老式短名（`bjfs2680.26o.gz`，**RINEX 2**）。
   ⇒ **只用 `d`**，而且只认 `.crx.gz` 结尾的那种 ——
   BJFS / CHAN 只有 RINEX 2 的份，会被判成"这个站没有"。
   **那是对的**：宁可说没有，也不能给一份下游用不了的。

### ⚠️⚠️ 44 倍的差距，以及它为什么**不能靠写死顺序解决**

同一个站同一天（WUH2，2026-09-25），两个源实测：

| 源 | 速度 | 一整份 |
|---|---|---|
| 武大 | **1305 KB/s** | 整条链 **9.4 秒**（含 4.9 秒 CrinEX 解码） |
| GA | **22 KB/s** | 5 MB 要 **3.8 分钟** |

根因：**GA 的观测下载指向 AWS S3 `ap-southeast-2`（悉尼）** ——
那个区从这台机器上就是慢（产品桶 `peanpod` 同区，本文件早就记过）。

⚠️⚠️ **而"谁排第一"写死在代码里必然是错的** —— 换个用户、换个地区就可能反过来。
   我第一版就是写死"武大第一"，还配了条守卫守着那个顺序。
   **用户点破了：「不是谁在前，是测一下速，用最快的」。**
   ⇒ 改成下载前**实测测速**（`fetch._rank_by_speed`），顺序只当兜底。

### ⚠️⚠️ 我在测速探针里写出的一个**反向 bug**（值得记）

第一版判据写的是：**「量到的窗口短于 1 秒 ⇒ 不可信 ⇒ 放弃这个源」**。
本意是"短窗口不可信"（这条教训本文件有好几处），
**但对快的源恰好反了**：

    武大 **0.8 秒就把 256 KB 下完了**（≈1300 KB/s）
    ⇒ 被那条判据判成"测不准" ⇒ **最快的源被扔掉**
    ⇒ 剩下的只有慢的能被量出来 ⇒ **GA（22 KB/s）反而排到了前面**

> **一个把"太快"当成"测不准"的判据，会让测速系统专门挑慢的用。**

⇒ 判据换成**字节数**（拿到了就是一次有效测量），时间只做**上限**（太慢才放弃）。
   守卫：`check_network` ⑯（含"秒传的源也要量得出来"这一条）。

### 那几个数字（免得下次重测）

    武大观测测速   3 轮：1272 / 1168 / 1241 KB/s
    GA 观测测速    3 轮：None / 60 KB/s / None   ← 多数时候慢到量不出来
    整条链（下载→截尾→gunzip→CrinEX 解码）：
        网络 3.7 秒 + gunzip 0.0 秒 + **解码 4.9 秒** = 8.6 秒
        产物 45,678,930 字节的明文 RINEX 3.05

⚠️ 端到端实测（走 app 自己那条路）：WUH2 **13.7 秒**、ALIC **19.5 秒**，
   都落在武大上 —— 和上面这些数吻合。

## 七点二十四、⚠️⚠️ 「猜出来的路径」是怎么活成"事实"的（2026-09-29）

## 七点二十五、⚠️⚠️ `requests` 会**自己去读** `~/_netrc` —— 于是"匿名测一下"是个陷阱（2026-09-29）

### 踩的过程

我想量"CDDIS 的老数据要不要账号"，就造了个**不带认证**的会话去下：

```
net.build_session(None) + cddis_get  →  200 + 真数据（`1f 9d`）
```

差一点写下「CDDIS 的老数据不用账号」。用 `curl`（真匿名）一对照：**302**。
两边对不上，才查出原因。

### 原因

`requests` 在 `trust_env=True`（**默认**）时会自己去找 `~/.netrc` / `~/_netrc`
（`Session.prepare_request` → `get_netrc_auth`），
而且**跟跳转时 `rebuild_auth()` 还会再补一次**。

⇒ 这正好解释了本仓库一条一直没解释透的现象：
**为什么"内建的 netrc 流程"能过 CDDIS，而"显式设的 auth"不能。**
`rebuild_auth()` 在跨主机时会把 `Authorization` 删掉，然后**只重新补 netrc 那一种**；
我们显式设的 `ScopedBasicAuth` 不在它的重补名单里。

### 两条实践含义

**① 在这个项目里，"匿名测一下"必须写成 `session.trust_env = False`。**
只要家目录里有一份 `.netrc`，任何"匿名"探针都是假的。

**② 本程序写的凭据在软件目录（`netrc_paths()`），而 `requests` 只认家目录。**
所以凡是"拿普通会话去碰 CDDIS"的代码，都会退化成
**"只有这台机器恰好有份老 `.netrc` 时才通"**。

⚠️ 而**本机恰好有那一份**（`C:\Users\<用户>\_netrc`，迁移之前留下的）——
所以那个 bug 在本机一直是**绿的**。实测把 `trust_env` 关掉：

| 会话 | trust_env | 结果 |
|---|---|---|
| `cddis_session` + `cddis_get` | True | ✅ 真数据 |
| `cddis_session` + `cddis_get` | **False** | ✅ **真数据**（自足） |
| 普通会话 + `cddis_get` | True | ✅ 真数据（**靠家目录那份**） |
| 普通会话 + `cddis_get` | False | ❌ 登录页 |
| `cddis_session` + `probe_url`（`allow_redirects=True`） | False | ❌ 登录页 |

### 它咬到的那一处：侧栏的 CDDIS 探测

`ginan/probe.py` 那条探测原来用**普通 GET**（`net.probe_url`），
于是：**用户填完凭据、「保存并验证」都通过了，侧栏仍然显示「需要登录」，而且永远不变。**
（`app.js` 里还写着注释期待它变绿 —— 它绿不了。）

⇒ 已改成走 `cddis_get`（`probe._probe_authed`），并且**只有标了"要账号"的源**走这条路，
其余源仍然是普通 GET（有对照守卫盯着，见 `check_network.py` ⑳a）。
探测地址也换成了实测存在的那一个（原来是那条 404 的死路径）。

> 👉 这一条最值得记的不是"改了个 if"，而是：
> **本机有一份残留文件，把一个用户可见的 bug 盖了很久。**
> 判据要能**模拟干净环境**，否则"我这儿是好的"什么都证明不了。

**① 「处理没有完成」—— 可它明明跑完了。**

**一个 "residual" 字样都没有。** 于是这些行全都落进了兜底的 `unrecognized_error`

—— 一个从句子中间截出来的碎片。

>   `diagnostics.py` 顶上那句"这些模式全部来自实测的 pea 输出"必须真的做到。

> 👉 守卫已经补上：`check_diagnostics.py` 里现在有一张
>   **真实输出行**的表（每行都带实测次数），逐条断言它落进哪个 kind，
>   并且断言它**不许落进兜底**。变异验证：把 `large_residuals` 改回原措辞 → 6 条红。

比硬塞进 warning 再想办法过滤要干净。

## 七点二十七、⚠️ 历元计数：**用 `-n` 截断时，日志比产物少 1**（2026-09-29 实测）

`diagnostics._EPOCH` 只数 `Processed epoch #` 那种行（另一种是不带 `#` 的反向解，
数了会**正好翻倍**）。这条规则是对的，但它的**适用范围比原来记的窄**。

实测（真跑，`brdc2sp3` / ALIC / 2026-09-02，app 自动传 `-n 96`）：

    日志里 `Processed epoch #` 的行数        95
    最后一条日志的历元                       23:30:00
    产物 SP3 头部声称的历元数                96
    产物最后一个历元的时刻                   23:45:00   ← 那一历元**真的算出来了**

⇒ Ginan 在 `-n` 到点时会**先写产物、再跳出循环**，最后那一历元不打日志行。

⚠️ 而原来记的那句「`grep -c 'Processed epoch #'` = 真实的历元数（2880）」
是拿**跑到自然结束**那次量的（观测读完了就停，走的是另一条出口）——
**两种出口下这个计数不一样。**

⚠️ 这件事变得要紧，是因为**本程序现在每次都传 `-n`**（那是我加的刹车），
所以结论里那句"（N 个历元）"**系统性偏小 1**。

**处置：知道就行，不去给这个数 +1。** 理由：自然结束那条路上它是准的，
加一会把它弄错；而**产物自己写着真实历元数**（SP3 头部 / `.POS` 里的有效历元），
需要精确时该去读产物 —— 而 `.POS` 那条路本来就在结论里另说了一个数
（"有效解算 N 个历元"，那个是精确的）。

## 七点二十八、作图：Ginan 自己能画什么，我们画了哪些（2026-09-29 实测）

### 一、先把 Ginan 的绘图能力摸清（扫全树，不是看 README）

`ginan-dist/ginan-main/` 里真正会画图的代码有 **6 处**，
C++ 源码里**一处都没有**（`src/` 下没有 `.py`/`.m`；
只有 `mongo.cpp` 的注释说"数据写 Mongo 供 Python 工具绘图"）：

| 文件 | 画什么 | 需要什么库 |
|---|---|---|
| `scripts/plot_pos.py`（698 行） | `.POS` 的 4 张图 | numpy + pandas + **statsmodels** + plotly |
| `scripts/plot_trace_res.py`（3357 行） | `.TRACE` 残差的 10 来张图 | numpy + pandas + plotly |
| `scripts/plot_spp.py` | `.SPP` 的 3 张图 | numpy + pandas + plotly |
| `scripts/plotting/ztd_plot.py` | ZTD 对照（PEA vs Bernese） | matplotlib + boto3 |
| `scripts/plotting/obs_code_plot.py` | RINEX 观测值/SNR | matplotlib + georinex |
| `scripts/ssrMonitoring/analyse_orbit_clock.py` | 轨道/钟差差异 + RMS 柱状 | matplotlib + gnssanalysis |
| `scripts/GinanEDA/`（整套 Web 应用） | 8 个 tab | **MongoDB** + Flask + plotly |
| `scripts/plotting/plotAtt.m` | 卫星姿态 GIF | **MATLAB** |

官方 `scripts/requirements.txt`：`pandas` / `scipy` / `statsmodels` / `matplotlib`
/ `boto3` / `pymongo` / `dash` / `scikit-learn` / `hatanaka` / `gnssanalysis` …

### 二、我们做了哪些，以及**为什么另一些做不了**

| Ginan 的图 | 我们的状态 |
|---|---|
| **POS 三维时序**（误差棒 + LOWESS + 加权均值 + ±2σ 带 + 每分量统计） | ✅ **做了**（`ginan/charts.py`，逐条对着 `plot_pos.py:165-298`） |
| **dN–dE 平面散布**（**1:1 等比例** + 按合成 σ 上色） | ✅ **做了**（`plot_pos.py:300-389`） |

| POS 地图（mapbox 底图） | ❌ **不做**：要在线底图（我们离线），而且**静态站的经纬度几乎不动** —— 那是给动态平台看的图 |
| SPP 那三张 | ❌ **没数据**：我们没有产出 `.SPP` 的工作流 |
| TRACE 残差那 10 来张 | 🟡 **要重跑**（见下） |
| ZTD 对照 | 🟡 只能出我们这一侧（Bernese 那份拿不到） |
| 轨道/钟差差异 + RMS 柱状 | 🟡 我们的 `compare_orbits` 有那个数据，还没画 |

| RINEX 观测值/SNR | ❌ 现在只解析头部，没读观测值 |
| 卫星姿态 GIF | ❌ 要 MATLAB + C++ 调试开关注释 |

### 三、⚠️ 残差图：**不是读一下现有文件就行**

实测（我们的运行目录）：

    .TRACE 大小                     4.9 MB
    残差行（`%` 开头的那些）          0 行

因为我们的配置**故意把 trace 调低了**（`config.py`：`trace.level = 1`、
`output_residuals = false`）—— 那是为了不让每次运行都写上百 MB 的产物。
而官方示例级别产出的 TRACE 是 **141 MB**（`official/out_example/` 里那份）。

⇒ 残差图要用**更高的 trace 级别重跑一次**。这是真取舍（磁盘/时间换诊断），
所以它该是"用户要看残差质量时"才走的路径，不能拖累默认路径。

### 四、两个"照抄但看着不一致"的地方（**故意照抄的**）

`plot_pos.py:127-145` 的 `compute_statistics`：

    w = 1/σ²     加权均值 = Σ(wx)/Σw      std = sqrt(Σ(w(x-wm)²)/Σw)   ← 加权
    RMS = sqrt(mean(x²))                                              ← **不加权**

⚠️ RMS 不加权、而 std 加权，**看起来不一致，但照抄** ——
   我们的数字要和 Ginan 自己的图对得上。改了就成了"看着一样、其实不一样"。
   守卫 `test_weighted_stats_match_ginan` 专门盯这一条（含"RMS 与 σ 无关"）。

### 五、⚠️ LOWESS：我们没引 statsmodels，但**结果必须一模一样**

Ginan 用 `statsmodels.nonparametric.smoothers_lowess.lowess`（`plot_pos.py:6`）。
它要拖 scipy+pandas（**+228 MB**），而我们要的只是一条平滑曲线 ⇒
自己实现（`ginan/series.py`），但**靠数值等价兑现**，不是靠"看着像"：

    实测（25160 个历元的真 .POS，五个 frac）      最大差 1e-14 米
    实测（501 点，frac=0.15）                     最大差 7.8e-15

⚠️ **邻域大小的取整约定是钉出来的，不是猜的**：statsmodels 用
   `k = floor(frac·n)`，我第一版写的是 `ceil` —— 在 501 点、frac=0.15 上
   差 **3.5e-3**（可见的量）。逐个试 k 的取整方式才定位到：

    frac=0.15  ceil(76) → 差 3.5e-3      floor(75) → 差 7.8e-15
    frac=0.5   ceil(251)→ 差 2.6e-3      floor(250)→ 差 6.8e-15

⇒ 守卫用**黄金值**（开发机上用 statsmodels 0.15.0 算出来抄进去的常量）盯死，
  这样 statsmodels **不需要成为本程序的依赖**，而等价性仍然被守着。
  变异验证：把 floor 改回 ceil → 3 条红。

### 六、送图到界面的方式：**figure JSON，不是 `to_html`**

`requirements.txt` 里那条被注释了很久的计划写的是"输出 HTML 图表，前端直接嵌"。
真做的时候发现**那条路不通**：`fig.to_html()` 产出 `<div>` + `<script>`，
而 `<script>` 插进 `innerHTML` **不会执行**（浏览器规定）。

⇒ 改成：服务端 `fig.to_json()` → 前端 `Plotly.newPlot(el, fig.data, fig.layout)`。
配一份**随包的** `frontend/plotly.min.js`（4.59 MB，从 plotly 包里拷的，
所以版本严格一致）—— 这个程序要在离网/内网可用，用 CDN 等于图全都不出来。

⚠️ 图**不塞进对话**：对话是模型说的（可以错），图是从产物直接画的（确定性）。
   两样东西的可信度不一样，混在一起用户分不清哪个是"算出来的"。


## 七点二十九、9 项改正**逐项量了一遍**：只有固体潮是大项（2026-10-01 实测）

### 怎么量的

同一份观测（ALIC 2026-09-02，2880 历元）、同一套配置（「完整」档、9 项全开），
**只翻一个开关**跑第二遍，比两次解的**平均位置**差多少、重复性变多少。

脚本与产物：`ginan-testdata-202506/corr_exp/`（`run_corr.py` + `corr_results.json`，
每次跑约 80~105 秒）。判据只用到 `.POS` 本身（不需要权威坐标）——
量的是"这一项算不算得出来"，不是"准了多少"。

### 结果

| 关掉这一项 | 解移动（三维） | 往哪动 | 重复性 |
|---|---|---|---|
| **固体潮** | **8.33 厘米** | U +8.25 | 2.94 → 3.53（**关了更差**） |
| 固体极潮 | 0.92 | U +0.89 | 2.937（没变） |
| 二阶电离层 | 0.26 | U −0.26 | 2.94 → 2.95 |
| 海洋极潮 | 0.08 | — | 2.937 |
| 海潮负荷 | 0.07 | — | 2.94 → 2.96 |
| 大气潮负荷 | 0.03 | — | 2.93 |
| 三阶电离层 | 0.0006 | — | 2.938 |
| 日月/行星历表（DE436） | 0.0001 | — | 2.937 |
| 海潮位势（fes2014b） | **0.0000** | — | 2.937 |

**结论：这 9 项里只有固体潮是真的大项**，其余 8 项加起来不到 1 厘米。
这解释了一件旧事：为什么「完整」档的**重复性反而略差**
（见 `config.PROFILES` 的 `standard.tradeoffs`）——它多算的那 8 项加起来
远小于噪声底（2.9 厘米），而修正越多、天线型号缺失带来的偏差越藏不住。

### 两个副产物

⚠️ **① 海潮负荷在本站几乎没有**：`OLOAD_GO.BLQ` 里 ALIC 的径向 M2 振幅是
   **2.5 毫米**（海湾里的站），所以量到 0.07 厘米是**对的**，不是"开关没生效"。
   开阔海域的沿海站会大得多 —— 这张表不能当普适结论用。

⚠️ **② 这条流水线是确定性的**：两个"配置完全相同"的变体跑出来
   位移是 **0.0000 厘米**。所以几毫米量级的差不是噪声，是真的效应 ——
   这也是上面那张表敢写到小数点后两位的理由。

⚠️ **③ 去掉 DE436（8.9 MB）解一点没变**：Ginan 退回它自带的解析星历
   （`planets.cpp`：`jplEphPos` 失败则走 `iauEpv` / `iauMoon`），
   在这份数据上够用。**"更精确的输入"不等于"结果会变"** ——
   这一条和"完整档不更准"是同一个道理，只是更极端。

### 怎么进的产品

`ginan/corrections.py` 里那 9 条 `effect` 就是上面这张表（逐项写清
"实测：解移动 X 厘米"）。UI 在设置面板里，9 个勾 + 每项的文件要求
（含大小、在不在本地）+「全部恢复默认」。
设计决策与被否掉的四个方案见 `decisions.md` ADR-012。


## 七点三十、残差：**要三个开关同时打开，而它在"网络"那份 trace 里**（2026-10-01 实测）

### 用户要的是"数据本身好不好"

位置的图回答"这次解稳不稳"，回答不了"**数据好不好**"。那要残差。
Ginan 自己有一份 3357 行的 `scripts/plot_trace_res.py` 画的就是它。

### 三个开关（缺一条都是**静默**的）

    outputs.trace.level: 5                ← 级别不够，**连块头都不写**
    outputs.trace.output_residuals: true
    outputs.trace.output_network: true    ← PPP / RTS 的残差在**这一份**里
    outputs.trace.network_filename: ...

实测（ALIC 2026-09-02，60 个历元，同一份配置只改 trace）：

| 配置 | 残差行 | `.TRACE` 大小 |
|---|---|---|
| level 1 + `output_residuals` | **0** | 7.0 MB |
| level 3 + `output_residuals` | **0** | 22.1 MB |
| level 5 + `output_residuals` | 4236 | 32.5 MB ← **只有 `RESIDUALS/SPP`（预处理阶段的码残差）** |
| level 5 + **网络 trace** | 18460 | **6.4 MB** ← `RESIDUALS/PPP` + `RESIDUALS/RTS` 都在，**而且更小** |

⚠️⚠️ **最后一行是这次查出来的关键**：只开 `output_receivers` 时，
PPP 和 RTS 那两段残差**根本不写** —— 而 Ginan 自己的脚本用的正是它们
（它的默认是"用平滑后的 RTS 残差，更准"）。我们一开始拿到的
"残差"全是预处理阶段的码残差，**很容易以为那就是全部**。

### ⚠️ 级别不影响解算（这是整件事的前提）

同一份配置，level 1 跑一遍、level 5 跑一遍：**`.POS` 逐字节相同**
（sha256 一致）。所以"开残差重跑一次"是**纯观测动作** ——
诊断看到的就是用户手上那份解的残差，不是另一次解算的。

### 一整天的实测（网络那份，2880 历元）

| | |
|---|---|
| 耗时 | **148 秒**（level 1 那次是 107 秒，差 41 秒） |
| `NET_*.TRACE` | 144 MB，39.0 万行 → 去掉后验中间迭代后 **17.7 万条** |
| `NET_*_smoothed.TRACE` | 52 MB（RTS，`iter = -1`） |
| 接收机那份 | **关掉**（level 5 下它自己就要 ~1.5 GB） |
| 归一化残差 | 码 σ=0.59、相位 σ=0.92（理想是 ≈1） |
| 超 3σ | 码 0.00%、相位 0.64% |

⚠️ 60 历元那份按比例外推是 300 MB，**整天实测只有 196 MB** ——
外推偏高（文件有固定开销，历元越多单位成本越低）。**外推要标出来。**

### 两个坑

⚠️ **① 平滑那份 `.TRACE` 的 `sigma` 整列是 0**（`prefit` 也是 0，
   只有 `postfit` 是真的）。所以**归一化残差在那份里算不出来** ——
   不检查的话会报成"0 条，超过 3σ 的占 0.00%"，看着像完美。
   要看归一化残差得读 **PPP** 那份（`NET_*.TRACE`）。

⚠️ **② 相位那组约 1.9% 的残差恰好是 0**（不是四舍五入）。
   直方图中间会有一根尖峰。**成因我们没查**（推测是"定义该卫星模糊度的
   那一条观测"，但**这只是推测**）。UI 上写明了"别把那根尖峰读成
   残差特别好"。

### 怎么进的产品

`ginan/tracefile.py`（解析 + 统计 + 结论）、`charts.py` 里那四张图
（残差随时间 / 归一化分布 / 每颗卫星 / 每个频点）、
工具 `run_residual_diagnostics`（重跑一遍 + 压成几百 KB 的派生文件）、
`/api/residuals` + `/api/residual_figures`。
⚠️ 那几百 MB 的 `.TRACE` **原来不自动删**（同 repro 的规矩：删不删用户定）——
**2026-10-02 起改了**：`「新任务」会整个清空运行目录`（`userdata/runs/`），
中间文件、结果、**连这份派生文件（`residuals/residual_summary.json`）一起走**
（理由见 `ginan/runs.py` 的文件头）。
要留的话，趁那份运行还在的时候把 `residuals/` 那个目录拷出来（几百 KB）。
